- **状态**：`implemented`（M3 已实现并通过验收；开工核对修订见
  `implemented/architecture/2026-08-16-m3-tools-决策.md`）
- **前置**：M2（已完成）。依赖 M2 的：LLM seam（工具调用协议走同一 seam）、agent loop
  （工具循环是"assistant 之后、turn/end 之前"的增量，loop 结构不推翻）、假 LLM（M2 决策 2
  已预留"工具调用序列 M3 用"）、tool 事件词汇（M1 已定义 `tool { name, input, output? }`）。
- **依赖关系**：M2 回答了"日志由谁产生"，M3 回答"模型只说不做怎么办——让它动手"。
  M4 的 tool 卡片直接渲染 M3 落的 tool 事件；M5 的 Trajectory 检查器读 tool 事件的 input/output。

## 目标

定义 **Tools seam**（注册表 + 执行管线，**预留 approval hook**），实现 **bash + 文件读/写/编辑**
工具，给 agent loop 装上**工具调用循环**：模型要工具 → 落 tool 事件 → 执行 → 结果回填模型 →
再问模型，直到模型给最终回答或达到步数上限。每个动作全部落 M1 词汇事件。

## 关键设计决策（预拍板，M3 开工时逐条核对）

1. **Tools seam**：抽象服务 `tools`（根 ctx 提供，loop 消费）。工具 = 声明（name/description/
   参数 schema）+ 实现（execute）。执行管线分三步：pre-execute（**approval hook 预留位**，
   MVP 直接放行）→ execute → post-execute（结果整形）。未来 approval 栈、MCP 工具都从这个
   seam 挂进来（requirements §8）。
2. **工具调用协议**：沿用 OpenAI 兼容的 `tool_calls`（adapter 增量：请求传 `tools` 定义、
   响应解析 `tool_calls`、历史里传 `role:'tool'` 结果消息）。假 LLM 增量：预设工具调用序列
   （M2 已留接口位）。
3. **loop 增量（不推翻 M2 结构）**：`llm.chat` 返回 tool_calls → 逐个落 `tool` 事件
   （{name, input}）→ 走 tools seam 执行 → 结果落 `tool` 事件（{name, input, output}）→
   结果回填 messages → 再调模型。循环直到：模型不再要工具（正常收 assistant + turn/end）
   或达到 `maxSteps`（落 turn/end {reason:'crash'} 或开工定夺）。单步单个工具串行，
   多工具并行是 backlog。
4. **工具事件词汇**（M1 已定义，M3 落地语义）：一次工具调用落两条 `tool` 事件——
   调用（只有 input）与结果（带 output），中间隔着执行。这样轨迹检查器能区分"要了什么"
   与"得到了什么"。
5. **bash 工具**：`{ command, cwd? }` → stdout/stderr/exit code。教学版无沙箱（直接执行，
   文档明示风险）；approval hook 位在 pre-execute。
6. **文件工具**：read/write/edit 三个独立工具（读/写/编辑各一个声明）。路径相对会话 cwd
   解析；无沙箱（同上）。
7. **cwd 来源**：会话 meta 携带 cwd（M2 的 SessionMeta 已有 title/createdAt，M3 增 cwd 字段，
   JSONL 头记录天然兼容——旧会话缺省用进程 cwd）。
8. **工具声明进模型输入**：M2 说"工具描述的注入是 M3 的事"——由 tools seam 提供声明列表，
   经 adapter 的 `tools` 参数传给模型（OpenAI 兼容协议原生支持）；是否同时拼进 system prompt
   由开工核对时按协议细节定夺。

## 任务拆解（按 TDD 顺序）

### 1. test-support 假 LLM 增量（RED→GREEN）

- `createFakeLlm` 支持工具调用回复：预设 `tool_calls` 序列（与普通文本回复混排），
  断言"loop 让模型看了什么工具结果"。

### 2. `packages/tools` 包骨架 + Tools seam 契约（RED→GREEN）

- 抽象服务 `tools`：注册/查找/声明列表 + 执行管线（pre-execute hook 位 → execute →
  post-execute）。契约测试：注册表、未知工具报错、管线顺序、approval 拒绝位（预留但
  MVP 放行）。
- 教学 README：第三个 seam——"loop 之外的能力从哪来"。

### 3. bash + 文件工具（RED→GREEN）

- bash：stdout/stderr/exit code 透传；命令执行失败也算"成功的结果"（exit code 是输出不是
  异常——模型需要看到失败原因）。
- 文件 read/write/edit：契约测试（读写往返、edit 的精确替换、路径解析、不存在报错）。

### 4. adapter 增量（RED→GREEN）

- 请求传 `tools`（由 loop 传入）；响应解析 `tool_calls`；历史里 `role:'tool'` 结果消息的
  序列化。

### 5. loop 工具调用循环（RED→GREEN）

- 多步循环测试：假 LLM 序列 [要工具 → 要工具 → 最终回答]，断言日志 =
  turn/start → user → assistant(带 tool_calls 的表征) → tool(调用) → tool(结果) → … →
  assistant(最终) → turn/end；模型每步收到的 messages 含上一步工具结果。
- maxSteps 上限：超限落 turn/end {reason:'crash'}（或定夺），不静默空转。

### 6. 端到端（RED→GREEN）

- 最小 runtime + 真 bash/fs：模型"读文件→改文件→回答"真实完成，全量事件入日志，
  resume 后历史完整。

### 7. 演示脚本 + 教程

- `packages/agent/examples/` 或 `packages/tools/examples/`（开工定夺）：零 key 工具 demo
  （假 LLM 剧本：读文件 → 改文件 → 总结）。
- 教程 `docs/tutorials/M3-tools.md` + 索引 + 小白验收。

## 教程交付（requirements §5.1）

`docs/tutorials/M3-tools.md`：

- **动机**：模型只会说不会做；工具让 loop 变成"手脚俱全"的 agent；为什么工具事件在
  Trajectory 里是灵魂的一半
- **design**：工具循环时序图（plantUML：tool_calls → 落 tool 事件 → 执行 → 回填 → 再问）、
  Tools seam 类图（注册表/管线/approval hook 位）
- **新概念**：工具调用协议（tool_calls/tool 消息）、执行管线与 hook、函数 schema、
  maxSteps（循环上界）、exit code 为什么是输出不是异常
- **tradeoff**：为什么无审批栈但 hook 位先留好；为什么一次工具调用落两条事件；为什么
  bash 无沙箱（教学版明示风险）；为什么工具结果回填 messages 而不是"记住在别处"
- **动手练习**（零 key）：给假 LLM 写一段"读文件→改文件"剧本跑 demo；手写一个自定义工具
  注册进去看循环跑起来；进阶：断言多步循环的完整事件序列
- 更新 `docs/tutorials/README.md` 索引

## 明确不做（防越界）

- 不做审批/权限栈（backlog #2；M3 只留 hook 位并默认放行）。
- 不做多工具并行调用（backlog；M3 单步单工具串行）。
- 不做 MCP、LSP 接入（backlog #6）。
- 不做工具超时/取消（backlog）。
- 不做 Web 的 tool 卡片 UI（M4 消费 M3 的事件即可）。
