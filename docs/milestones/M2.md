# M2 —— LLM seam + 假 LLM + agent loop

- **状态**：`proposed`（M1 收尾时定稿；进入 M2 前可再修订，修订记入 notes）
- **前置**：M1（已完成）。依赖 M1 的：Session 事件词汇（loop 每个动作落日志）、
  `openSession` 的子 ctx（loop 作为插件跑在会话 ctx 上、继承根注入的 LLM 服务）、
  `flush/resume`（端到端测试断言"重启后历史完整"）。
- **依赖关系**：M1 回答了"会话是什么（日志）"，M2 回答"日志是谁产生的（loop）"。
  M3 的工具调用循环是 loop 的增量；M4 的流式 UI 消费 M2 预留的流式 seam。

## 目标

定义 **LLM seam**（抽象服务，至少一个实现：OpenAI 兼容 adapter），做出 **假 LLM**
（test-support），写出**全仓唯一的 agent loop**：单轮 chat（user → turn/start → 模型回复 →
assistant → turn/end），每个动作全部落 M1 词汇事件。

## 关键设计决策（预拍板，M2 开工时逐条核对）

1. **LLM 是 seam**：抽象服务 `llm`，契约 `chat(messages, options) → { content, usage }`；
   流式接口在 seam 上**预留**（`stream` 或 `chat` 的流式选项），M2 的 loop 只消费非流式，
   流式接 UI 是 M4 的事。adapter 是第一个实现；假 LLM 是测试实现。
2. **假 LLM 放 test-support**（M0 已预留目录与命名）：可编程回复序列（M2 用）、工具调用序列
   （M3 用）、流式分片（M4 用）、延迟模拟（skill 契约）。零 key 验收全靠它。
3. **agent loop 是全仓唯一具体循环逻辑**（requirements §2.5、§7）：只此一处"拿输入→调模型→
   写输出"的循环，未来一切能力（工具、审批、compaction）都从 seam 挂进来，不改 loop。
4. **loop 的输入也来自日志**：从会话日志投影出 messages（`user`/`assistant` 事件 → 消息数组）
   作为 llm 输入——"日志是真源"的双向验证：输出写日志，输入读日志。投影辅助放 session 包
   （M1 明确"投影视图属 M5"，但 messages 投影是 loop 的输入刚需，属 M2）。
5. **loop 跑在会话 ctx 上**：`openSession` 之后 `session.ctx.plugin(agentLoop, config)`；
   LLM 服务由根 ctx 提供（JSONL 后端同款注入模式），换 provider = 换提供服务的插件。
6. **system-prompt 组合**：M2 最小——可配置字符串拼进 messages 头部；工具描述的注入是 M3 的事。

## 任务拆解（按 TDD 顺序）

### 1. test-support 假 LLM（RED→GREEN）

- `createFakeLlm({ replies: [...] })`：按序出回复、可编程延迟、记录收到的请求
  （测试断言"loop 给模型看了什么"）；回复用尽抛错（防静默空转）。

### 2. `packages/llm` 包骨架 + LLM seam 契约（RED→GREEN）

- 抽象服务 `llm`：`chat(messages, options)` 契约测试（定义 shape、错误传播、messages 顺序）。
- 教学 README：什么是 seam 的"第二个实例"（session-persistence 之后）。

### 3. OpenAI 兼容 adapter（RED→GREEN）

- 对接 DeepSeek API 的 OpenAI 兼容协议（`/chat/completions`）；HTTP 层可注入（fetch 或
  自定义 sender），测试用**假 HTTP 端点**（本地 mock），零 key 不真调 API。
- 契约：请求体组装（system/user/assistant 消息）、响应解析、usage 透传、错误传播。

### 4. `packages/agent` 包骨架 + agent loop（RED→GREEN）

- loop 插件：监听会话 ctx 的 `user` 事件 → emit `turn/start` → 日志投影 messages →
  `llm.chat` → emit `assistant` → emit `turn/end {reason:'done'}`；异常路径 emit
  `turn/end {reason:'crash'}`（或错误事件，M2 开工定夺）。
- 测试：假 LLM + 真 Session，断言**事件日志完整 turn 序列**（test-support recorder 或
  session.log）；"模型收到的 messages == 日志投影"。

### 5. 端到端（RED→GREEN）

- 最小 runtime：JSONL 后端 + 假 LLM + SessionManager + loop；聊一轮 → 落盘 → 模拟重启 →
  resume → 历史完整且 loop 可继续。

### 6. 演示脚本 + 教程

- `packages/agent/examples/`（沿用 M0/M1 约定）：零 key 对话 demo（假 LLM 台词本）。
- 教程 `docs/tutorials/M2-llm-and-loop.md` + 索引 + 小白验收。

## 教程交付（requirements §5.1）

`docs/tutorials/M2-llm-and-loop.md`：

- **动机**：M1 的日志是"容器"，M2 让第一个"生产者"上岗；为什么 loop 是全仓唯一循环
- **design**：loop 时序图（plantUML：user 事件 → 投影 messages → llm.chat → assistant 事件）、
  seam 类图（llm 服务 + adapter + 假 LLM）
- **新概念**：adapter、agent loop、system prompt、上下文（context）、投影成 messages（M1
  预告的投影第一次落地）、服务注入链（根提供、会话消费）
- **tradeoff**：为什么 loop 输入也读日志（不另存一份消息数组）；为什么先非流式（流式留给 M4
  UI）；为什么 adapter 走 OpenAI 兼容协议（DeepSeek/Ollama/vLLM 通用）；为什么假 LLM 必须
  记录收到的请求（可观测性）
- **动手练习**（零 key）：给假 LLM 换台词本看日志变化；加一轮对话验证 resume 后续聊；
  进阶：断言"模型收到的 messages"精确内容
- 更新 `docs/tutorials/README.md` 索引
