# M1 —— Session 事件词汇 + JSONL 持久化 + resume

- **状态**：`implemented`（已完成：58 测试全绿、typecheck 绿、demo 与教程练习零 key 实测通过）
- **前置**：M0（已完成）。依赖 M0 的：测试 ctx 三件套（`@mini-dsh/test-support`）、cordis 组装、
  事件类型化方案（`declare module 'cordis'` 模块增强，已在 M0 实证）。
- **依赖关系**：本 M 是"事件日志是真源"（requirements §2.3）的落地。M2 的 agent loop 每走一步
  都要往日志落事件，M5 的 Trajectory 视图从此投影 —— 所以词汇与持久化必须先于 loop 存在。

## 目标

定义 **Session 事件词汇**（`turn/start`、`turn/end`、`user`、`assistant`、`tool` 等），做出
append-only 的 **Session 日志**与 **SessionPersistence seam + JSONL 后端**：会话能落盘、能
重开继续（resume），崩溃后 load 自动补一条 `turn/end`。

## 关键设计决策（已拍板，M1 照此实施）

1. **事件词汇 = cordis 事件名 + 类型增强**：在 `packages/session` 里
   `declare module 'cordis' { interface Events { 'turn/start'... } }`（M0 已实证该机制）。
   事件名即日志条目的 `type`。
2. **桥接模型（emit → append）**：agent/测试插件在**会话自己的 ctx** 上 emit 词汇事件，
   session 内部一个桥接监听器把事件**同步**追加进 append-only 日志；日志是唯一真源，
   emit 方不知道谁在记录。备选"直接调 session.append()"被否：那样 emit 与日志会存在两套
   行为路径，UI/测试无法统一"看事件"。（此取舍写入 M1 教程的 tradeoff。）
3. **持久化是 seam**：抽象服务 `SessionPersistence`（契约：`locate/create/append/load/list`），
   JSONL 后端是第一个实现；将来 SQLite 后端（backlog #4）只换实现。
4. **存储位置**：每个会话一个 `<dir>/<id>.jsonl`；`dir` 默认
   `<DSH_HOME 或 ./.mini-dsh>/sessions`，可经 options 覆盖。
5. **JSONL 格式**：每行一个 JSON 对象；首行为 `{"type":"session/created",...}` 头记录，
   之后每行一个 `SessionEvent`（`seq` 单调递增）。单文件追加，不做事务——崩溃窗口由恢复逻辑兜底。

## 任务拆解（按 TDD 顺序）

### 1. `packages/session` 包骨架

- 包名 `@mini-dsh/session`；依赖 `cordis`；devDep `@mini-dsh/test-support`（workspace:*）。
- 教学 README 说明"为什么词汇先于 loop"。

### 2. 事件词汇（RED→GREEN）

- `src/events.ts`：模块增强声明 `Events` 词汇 + `SessionEvent` 载荷类型
  （`seq`/`type`/`ts`/`payload`）。
- 契约测试（test-support 的 recorder 断言）：emit 每种词汇事件 → 桥接后日志中按序出现、
  载荷无损。类型层测试：`@ts-expect-error` 未声明事件名报错。

### 3. Session（内存日志 + 桥接）

- `src/session.ts`：`Session` 持有 append-only 事件数组（投影辅助如 `messages()` 属 M5 视图，
  **本 M 不做**）；创建时得到自己的子 ctx；在子 ctx 上 emit 词汇事件 → 桥接监听器 append。
- 测试：顺序保留、append-only（无修改/删除 API）、dispose 后不再记录。

### 4. SessionPersistence seam + JSONL 后端（RED→GREEN）

- `src/persistence.ts`：抽象 `SessionPersistence` 契约：
  `locate(id)` / `create(meta)` / `append(id, event)` / `load(id)` / `list()`。
- `src/backends/jsonl.ts`：JSONL 实现（读=按行解析，写=追加一行）。
- 契约测试（seam 测试）：create→append→load 往返、顺序、locate 缺失返回 undefined、
  多会话互不串、list 返回全部。**JSONL 实现必须全过；这份契约测试未来直接复用给 SQLite 后端。**

### 5. SessionManager（create / resume / list）

- `src/manager.ts`：服务 `SessionManager`（cordis `Service` 子类）：
  `create(meta)` → 新会话 + 落盘；`resume(id)` → load + 恢复（含崩溃修复）→ 返回可继续的
  Session；`list()` 交给 persistence。
- 测试：新建→（模拟重启：新 ctx 新 manager 实例）→resume 后历史完整、可继续追加。

### 6. 崩溃恢复

- 契约：load 时若日志以 `turn/start` 收尾（无配对 `turn/end`）→ 补写一条
  `turn/end`（标记 `reason: 'crash'`）并持久化；幂等（第二次 load 不再补）。
- 测试：手工构造"断尾"文件 → load → 事件末尾出现补写的 `turn/end` 且文件已落盘；再 load 一次
  数量不变。

### 7. 演示脚本 + 提交纪律

- `examples/`：无 LLM 的演示 —— 脚本创建会话、emit 一轮 `turn/start→user→assistant→turn/end`、
  落盘、重新 load 打印事件表（教程练习的基础）。
- 每步 RED/GREEN/REFACTOR 提交，中文 message（TDD skill）。

## 教程交付（requirements §5.1）

`docs/tutorials/M1-event-log.md`：

- **动机**：为什么 loop 之前先有日志词汇（M2 每一步动作都要有处安放；M5 轨迹要有的投影）
- **design**：事件流图（plantUML：emit → 桥接 → JSONL 落盘 → load/投影；崩溃恢复时序）
- **新概念**：append-only 日志、事件词汇（vocabulary）、真源（source of truth）、
  投影（projection，只预告不实现）、seam 换后端、崩溃恢复/幂等
- **tradeoff**：为什么"emit→append 桥接"而非直接调 append；为什么 JSONL 而非 SQLite；
  为什么单文件追加不做事务（恢复兜底 vs 复杂度）；为什么日志是真源而非"数据库行 + UI 状态"
- **动手练习**：零 key —— 脚本写一轮假对话 → 杀掉进程模拟崩溃 → 重开看自动补的 `turn/end`；
  进阶：给 JSONL 后端换一个 `dir` 观察文件布局
- 更新 `docs/tutorials/README.md` 索引
