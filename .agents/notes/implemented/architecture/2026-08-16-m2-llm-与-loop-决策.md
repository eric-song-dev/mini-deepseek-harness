## 核对结论（逐条，含实施中的修订）

1. **LLM seam**（决策 1，无修订）：
   `chat(messages: readonly ChatMessage[], options?: ChatOptions): Promise<ChatResult>`
   - `ChatMessage { role: 'system'|'user'|'assistant', content: string }`
   - `ChatResult { content: string, usage: ChatUsage }`，`ChatUsage { inputTokens, outputTokens }`
   - 流式预留：`ChatOptions { onChunk?: (chunk: string) => void }`——M2 的 loop 与 adapter 均不调用；
     M4 接 UI 时用同一 seam 消费增量（文档注明"预留"）。
   - 服务名 `'llm'`，cordis 模块增强照 M1 模式。

2. **假 LLM**（决策 2，无修订）：`createFakeLlm({ replies })` 按序弹出回复、可编程 delay、
   记录收到的请求（messages 快照）、回复耗尽抛 `FakeLlmExhaustedError`（防静默空转）。
   **类型结构化兼容 LLM seam**（test-support 不依赖 llm 包，避免 workspace 循环依赖；
   本地定义 `FakeLlmMessage` 与 `ChatMessage` 结构相同，TS 结构化类型使两者互赋）。
   M3 的工具调用序列从同一接口位扩展。

3. **agent loop 入口（决策 5 + 任务 4 修订 ⚠️）**：spec 原文"监听会话 ctx 的 user 事件"，
   核对后改为 **loop 提供服务，调用方 `loop.chat(content)` 驱动一轮**。理由：
   - 日志顺序要求 `turn/start → user → assistant → turn/end`（验收清单 + M1 roundtrip 演示约定）；
     Session 桥接在 openSession 时同步注册，若外部 emit user 再由 loop 反应，turn/start 必然
     排在 user 之后，与约定冲突。
   - 上游 agent-loop README 同款语义：**驱动器认领会话、先打开持久轮次（turn/start）再领取输入**，
     外部不直接 emit session 事件，而是把输入交给 loop（原版 `send()` 原语的迷你版）。
   - 因此 `turn/start` 与 `user` 都由 loop 自己 emit（外部生产者不碰轮次边界），
     这也是"loop 是日志唯一生产者"的体现。
   - 插件形态：`session.ctx.plugin(agentLoop, { systemPrompt? })`。

   **实施修订 a（loop 句柄位置）**：cordis 的 `ctx.plugin` 会给插件一个**会话 ctx 的子 ctx**
   （插件自己的 fiber 作用域），因此 loop 句柄用 `defineProperty` 挂在该子 ctx 上，
   调用方经 fiber 取：`const fiber = await session.ctx.plugin(agentLoop); fiber.ctx['agent-loop']`。
   不用 `ctx.provide`：cordis 服务键按**根 ctx 作用域唯一**（isolate 链共享，实施中实测撞键），
   并存会话各自 provide 同名服务会抛 "already registered"——与 M1 的 `events`、M2 的
   `session-log` 同款处理。

4. **异常路径定夺（任务 4 的"开工定夺"）**：`llm.chat` rejection → emit `turn/end { reason: 'crash' }`
   （M1 崩溃恢复词汇同款 reason），**并把原错误向上抛**（调用方可见失败；不吞错、不虚构
   assistant 内容）；不新增错误事件词汇（M3+ 再议）。
   **实施修订 b**：省略开工核对里的 `ctx.logger.warn`——事件（turn/end crash）+ 异常上抛
   已双通道可见，避免测试输出噪音。

5. **loop 输入读日志的通道（决策 4 细化 ⚠️）**：loop 需要"此刻的完整日志"来投影 messages，
   但 loop 插件拿不到 Session 对象的 `.log`。细化：**Session 在会话 ctx 上提供只读入口
   `'session-log'`**（`{ events: readonly SessionEvent[] }` 快照 getter）。
   - 这是"输出写日志、输入读日志"双向验证的落点；loop 每轮从 session-log 读日志再投影，
     不自己维护第二份消息数组（resume 历史天然正确，e2e 守护）。
   - M5 的 Trajectory 投影同样从这个服务读日志（seam 复用）。
   - 实现用 `Object.defineProperty` 自有属性遮蔽（并存会话撞键问题，同第 3 条修订 a）；
     类型增强 `ctx['session-log']`。

6. **messages 投影**（决策 4，无修订）：`projectMessages(events, { systemPrompt? })` 放 session 包，
   user/assistant 事件按日志顺序映射成消息、其余事件跳过、systemPrompt 拼头部（决策 6）。
   返回类型 `ProjectedMessage`（与 ChatMessage 结构化相同，loop 直接传参）。

7. **OpenAI 兼容 adapter**（决策 1 的"第一个实现"）：
   - `createOpenAiLlm({ baseUrl?, apiKey?, model?, fetch? })`：默认 baseUrl `https://api.deepseek.com`
     （DeepSeek API 即 OpenAI 兼容协议）、model `deepseek-chat`；POST `<baseUrl>/chat/completions`，
     body `{ model, messages, stream: false }`。
   - `apiKey` 可选：提供时带 `Authorization: Bearer`；不提供则不带头（Ollama/vLLM 等本地端点无需 key）。
   - HTTP 层注入 `fetch`（测试注入假端点，零 key 不真调 API）；响应解析
     `choices[0].message.content` + usage 映射（prompt_tokens→inputTokens 等）。
   - 非 2xx 抛 `LlmHttpError`（带 status）；网络/解析错误原样传播。
   - 插件形态 `openAiLlm(ctx, options)` 提供 `'llm'` 服务（JSONL 后端同款注入模式）；
     另加 `provideLlm(llm)` 通用提供插件——demo/e2e 用它注入假 LLM（"换 provider = 换插件"）。

8. **串行化**：loop 内部用 promise 链串行化 chat（一轮未结束不开始下一轮），
   测试覆盖"连续两轮按序各成完整 turn"（带 delay 的假 LLM 验证无交错）。

9. **函数插件的依赖声明（实施中实证）**：`agentLoop` 用 `Object.assign(函数, { inject: ['llm'] })`
   声明依赖——cordis 会等 `llm` 服务就绪再装载插件，setup 里 `ctx.llm` 才能取到
   （SessionManager 的 `static inject` 同款机制；`Object.assign` 形态保证 `ctx.plugin(agentLoop)`
   的 config 参数可省略）。

10. **seam 契约测试的 RED 信号**：LLM seam 是纯类型契约，`import type` 会被 vitest 运行时
    擦除——契约套件的 RED 信号是 **typecheck 失败**（cannot find module），而非测试红。
    已记入 RED commit message。
