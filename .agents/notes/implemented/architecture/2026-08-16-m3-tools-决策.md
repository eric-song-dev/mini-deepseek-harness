- **状态**：`implemented`（M3 已实现并通过验收；本文件由开工核对笔记归档并补实施修订）
- **依据**：`docs/milestones/M3.md` 的"关键设计决策（预拍板，M3 开工时逐条核对）"

## 核对结论（逐条，含实施中的修订）

1. **Tools seam**（决策 1，无修订）：
   `ToolsService { register / get / list / addHook / execute }`，工具 = `ToolDeclaration`
   （name/description/parameters JSON Schema）+ `execute(input, ctx)`。管线三步：
   **pre-execute hooks → execute → post-execute hooks**。语义定夺：
   - pre hook 只做"观察/拒绝"（抛 `ToolDeniedError`），**不改造 input**——approval 栈的最小
     挂点，保持契约最小；
   - post hook 返回值替换输出（结果整形），返回 `undefined` 表示不改。
   - 错误契约：未知工具抛 `UnknownToolError`（带工具名）；重名注册抛错（防静默覆盖）；
     工具实现抛错原样传播（管线不吞错）。
   - 服务名 `'tools'`，cordis 模块增强照 M1/M2 模式；插件形态 `toolRegistry`（提供默认
     注册表）+ `provideTools`（注入任意实现）+ 工具插件（bashTool/readFileTool/…，
     `inject: ['tools']`，Object.assign 形态）。
   - 契约测试 `tests/contracts/tools-contract.ts` 与 M1/M2 同款可复用套件。

2. **工具调用协议**（决策 2，细化 ⚠️）：沿用 OpenAI 兼容 `tool_calls`。seam 类型定夺：
   `ToolCall { id, name, arguments: Record<string, unknown> }` —— **arguments 是已解析对象**，
   wire 的 JSON 串 ↔ 对象的转换**全部归 adapter**（`toWireMessage`/`parseToolCalls`）。
   理由：seam 一贯哲学"协议细节关在实现里"（教程 §4.5）；非法 JSON 回退空对象、非法字段
   回退空串——模型输出不可控，别让一次坏参数打崩整个 loop。历史消息增
   `role:'tool' + toolCallId`（结果回填用）；`ChatOptions.tools` 由 loop 传入（决策 8）。
   **M2 契约的一个放宽**：M2 adapter 对"响应缺少 content"抛错；M3 起"只有 tool_calls、
   content 为 null"的响应合法（content 置空串）——工具调用回复本就无正文。

3. **loop 增量**（决策 3，无修订）：`llm.chat` 返回 toolCalls → 逐个落 tool 调用事件
   （`{name, input}`）→ `tools.execute` → 落 tool 结果事件（`{name, input, output}`）→
   **每步重新从 session-log 投影** messages（结果以 role:'tool' 消息进入下一步模型输入）→
   再调模型。循环出口：模型不再要工具（assistant + turn/end done）或 `maxSteps`。
   **M2"输入读日志"原则延伸到循环内部**：loop 在循环里也不攒消息数组——工具结果能进模型
   输入，完全因为它先落进了日志（resume 后工具往返自动复原，e2e 守护）。
   单步单工具串行；一个 assistant 回复的多个 toolCalls 逐个执行完再问模型（并行是 backlog）。
   插件依赖增为 `inject: ['llm', 'tools']`；工具执行的 cwd 从 `ctx['session-meta']` 取
   （决策 7），旧会话缺 cwd 用进程 cwd 兜底。

4. **工具事件词汇**（决策 4，无修订）：一次调用两条 `tool` 事件，调用（无 output）/结果
   （带 output），中间隔着执行。投影规则配套：结果事件映射成 role:'tool' 消息（content =
   `JSON.stringify(output)`），toolCallId 按"最近的 assistant toolCalls 顺序"配对（串行执行
   保证顺序对应）；孤立结果合成 `tool-<seq>` id；**调用事件（无 output）跳过**——结果没回来，
   模型不能看到半截。assistant 载荷增可选 `toolCalls`（M1 词汇向后兼容）。

5. **bash 工具**（决策 5，无修订）：`{command, cwd?}` → `{stdout, stderr, exitCode}`。
   定夺：`execFile('bash', ['-c', command])`；**非零退出码是正常结果**（`typeof error.code
   === 'number'` 分支），spawn 本身失败（cwd 不存在等，code 是字符串）才 rejection；
   maxBuffer 放宽 10MB（stdout 超限显式失败，不静默丢数据）。

6. **文件工具**（决策 6，无修订）：read/write/edit 三个独立声明（`read_file`/`write_file`/
   `edit_file`）。定夺：read 不存在**报错**（读不到就是读不到）；write 覆盖 + 父目录自动
   创建（工具要能"建新东西"），返回 `{path, bytes}`；edit 的"精确替换" = 旧文本**恰好一次**
   （0 次/多次都抛错且文件不动），返回 `{path, replaced}`。路径解析：绝对路径原样、相对
   路径按 `ctx.cwd`；**无沙箱**（README/教程明示风险）。

7. **cwd 来源**（决策 7，无修订）：`SessionMeta.cwd?` + `CreateSessionInput.cwd?`（可选字段
   = M1/M2 旧头记录兼容），JSONL create 缺省补进程 cwd。loop 取 cwd 的通道：Session 新增
   **`session-meta` 只读入口**（会话 ctx 自有属性遮蔽，同 session-log 机制）——比"从
   session-log 读头记录 payload"少一层位置假设。消费方兜底：`meta.cwd ?? process.cwd()`。

8. **工具声明进模型输入**（决策 8，定夺 ⚠️）：spec 留了"tools 参数 vs 拼 system prompt"，
   定夺为**只走协议的 `tools` 参数**（每步 `tools.list()` 传入，adapter 序列化成
   `{type:'function', function}` 包裹，未传时不发该字段）。理由：结构化 schema 对模型更可靠、
   不占 system prompt、注册新工具零 prompt 改动（教程 §4.6）。

## 实施修订（spec 之外的定夺）

- **a. maxSteps 超限路径**（spec 任务 5 的"开工定夺"）：落 `turn/end {reason:'limit'}`
  （**词汇新增**，区别于 crash 的语义——"没完没了被掐断" ≠ "坏了"，M5 检查器需要区分）
  + 抛 `MaxStepsExceededError` 上抛。默认上限 `DEFAULT_MAX_STEPS = 8`（教学版从紧）。
  catch 里按错误类型分流 limit/crash，两条路径都不吞错。
- **b. M2 测试 harness 的契约更新**：loop 的 inject 新增 'tools' 后，M2 的 loop/e2e 测试与
  demo 的 harness 全部补 `provideTools(createToolRegistry())`——这不是测试放水，是 loop
  消费契约的真实演化（loop 现在需要 tools 服务才能装载）。
- **c. 工具循环的 e2e RED 说明**：任务 6 的端到端测试直接绿——RED 阶段由任务 1–5 的单元
  测试承担（e2e 只是组合已测组件），已在 commit message 注明。
- **d. 教程练习脚本确定性**：`my-tools.ts` 每次运行重置种子文件（demo 是幂等续写，练习是
  确定性重置），保证"改剧本看变化"的练习可复现。
