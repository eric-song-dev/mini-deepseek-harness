# M0 技术决策：cordis 版本、API 契约、profile 格式、类型化方案

- **日期**：2026-08-16
- **状态**：`implemented`（M0 已完成，全部决策落地并经测试实证）

## 背景

M0 是仓库第一行代码。按 `docs/references/upstream.md` 的查阅协议，先核对了上游 clone
（`../deepseek-harness-upstream`，路径与文档一致，无需更新索引）与 npm registry，
确定以下决策。

## 决策

### 1. cordis 版本：`cordis@4.0.0-rc.8`（npm latest，官方包）

- 硬约束 §2.1 要求用官方 `cordis` npm 包。npm latest = `4.0.0-rc.8`（2026-08-10 发布）。
- 上游仓库 vendor 的是自维护的 `@deepseek-ai/cordis@4.0.1`（`vendor/cordis/`），**该版本未发布到 npm**；
  冲突时按 upstream.md 纪律：以 npm 官方包为准，本仓库只依赖 `cordis@4.0.0-rc.8`。
- rc.8 与 vendor 4.0.1 同属 cordis v4 一代，API 一致（Fiber/effect/events 服务化）。
- 注意：`cordis@3.x` 的 `@cordisjs/core` 仍在维护（3.18.1），API 完全不同（`ctx.provide` +
  `Context.service` 装饰器）。我们**不用 3.x**，因为官方 `cordis` 包的最新代是 4，教学应贴近
  上游现状；3.x 与新 vendor 的写法差异大，混用会误导学生。

### 2. cordis v4 关键 API 契约（照搬概念，自写实现）

读 rc.8 类型声明 + 上游 vendor README 的 Quick Start，提取的契约：

- `new Context()` 建根 ctx；`await ctx.plugin(plugin, config?)` 装载插件（返回 `Fiber & PromiseLike<Fiber>`）。
- 插件三形态：函数 `(ctx, config) => ...` / 类（`new (ctx, config)`）/ 对象 `{ apply(ctx, config) }`。
- 服务：`class X extends Service { constructor(ctx) { super(ctx, 'x') } }`；
  `Service` 基类构造器自动 `ctx.reflect.provide(name, self)`。函数插件要提供服务则手动 `ctx.provide(name, value)`。
- 依赖注入：插件声明 `inject: ['x']`（`Object.assign(fn, { inject })`）或 `@Inject()` 装饰器；
  之后 `ctx.x` 属性代理按 `internal/get` waterfall 解析。
- 事件：`ctx.on(name, listener)` / `ctx.emit` / `ctx.parallel` / `ctx.serial` / `ctx.bail` / `ctx.waterfall`。
- 生命周期：插件内副作用用 `ctx.effect(() => cleanup)` 注册，随 fiber 卸载自动清理；
  根 ctx `await ctx.fiber.dispose()` 整体关停。
- 内建：`ctx.logger`（LoggerService，`logger.info(...)` 可用）、`ctx.registry`、`ctx.events`。

### 3. 类型化方案：`declare module 'cordis'` 模块增强（**已实证：可用**）

上游 vendor README 的 Quick Start 用 `declare module 'cordis' { interface Context {...} interface Events {...} }`
做类型增强。**实证结论（探针 `@ts-expect-error` 全部按预期触发）**：rc.8 下增强生效——
`interface Context` 合入后 `ctx.<name>` 有类型；`interface Events` 合入后 `ctx.on/emit` 按事件名收窄，
未声明事件名与错误载荷都是编译错误。**M1 事件词汇就用这个方案**：`packages/session` 声明
`declare module 'cordis' { interface Events { 'turn/start'... } }`（声明文件必须 `import 'cordis'`）。
事件**运行时**始终走 cordis 事件总线，类型只是增强。

### 4. profile 格式（mini 版，M0 定稿）

照搬上游 profile 的"列表行"思想（上游 `*.cordis.yml` 是 `id/name/config` 的列表 + patch 叠加），
mini 版收窄为 M0 spec 的最小格式（patch 叠加属后续 M）：

```yaml
plugins:
  - name: '@mini-dsh/xxx'      # 裸包名，Node 包解析
  - name: './plugins/hello.ts' # 相对路径，相对 profile 文件所在目录
    options: { greet: 'hi' }   # 可选，原样传给插件的 config 参数
```

- `options` 一词与 M0 spec 一致；上游叫 `config`，差异记录在 kernel README。
- 校验：手写最小校验（缺 name / name 非字符串 → 抛带行号的错误），不引 schemastery（教学先讲最小实现，
  复杂 schema 留给后续需要它的 M）。

### 5. 脚手架与工具链

- pnpm workspaces（`packages/*`），包 scope `@mini-dsh/*`；Node ≥ 22.19（本机 22.19.0），ESM 全仓。
- TypeScript `~5.9.3`：**不用 TS 7**（npm latest 7.0.2 是新的原生编译器，教学项目先求稳；
  5.9 是 5.x 末代，vitest/编辑器生态兼容性最好）。根 `tsconfig.base.json` 严格模式，各包继承。
- Vitest `^4`：单根 config（`include: packages/*/tests/**/*.test.ts`，environment: node）；
  M4 上 Web 测试时再拆 workspace（jsdom 项目），到时记入该 M 的 notes。
- **模块解析用 `module: ESNext` + `moduleResolution: bundler`（实证决定，不用 NodeNext）**：
  cordis@4.0.0-rc.8 发布的 `lib/*.d.ts` 内部是**无扩展名的相对导入**（`export * from './context'`），
  在 `moduleResolution: NodeNext` + ESM 模式下解析失败（TS2305 级联）。本项目是**源码直用的 monorepo**
  （包 exports 直接指 `src/index.ts`，vitest/tsx 消费，无 emit 步骤），bundler 解析本来就是正解；
  相对导入写无扩展名形式，与 bundler 语义一致，教学上少一个坑。若将来要发布编译产物，再引入构建步骤。
- `tsx` 跑 demo 脚本（kernel 示例 profile 的启动演示）；`yaml@^2` 解析 profile。
- 包间引用走包名（`@mini-dsh/*`，exports 直接指向 `src/index.ts`，无构建步骤）：
  教学上直观展示 monorepo 边界，tsc/vitest 原生支持。
- npm cache 已被 root 文件污染（历史 bug），**全部用 pnpm**，不动 npm。
- pnpm 11 依赖构建批准用 `pnpm-workspace.yaml` 的 `allowBuilds: { esbuild: true }`（esbuild 需平台二进制）。

### 6. test-support 公共 API（M0 范围）

- `createTestContext()` → `{ ctx, dispose }`（真 cordis Context，无假 LLM —— 假 LLM 属 M2，
  目录与命名预留）。
- `defineTestService(name, impl)` → 函数插件，装载即 `ctx.provide(name, impl)`。
- `createEventRecorder(ctx, names)` → 记录指定事件名的 `{ name, args, seq }` 序列 + 过滤/断言辅助。
- kernel 的 `loadProfile(path)` → `{ ctx, dispose }`；`parseProfile(source)` 单独导出供契约测试。
