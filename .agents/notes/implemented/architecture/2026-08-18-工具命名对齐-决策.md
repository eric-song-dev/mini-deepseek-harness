# 工具命名对齐上游（C1 #1）

- **日期**：2026-08-18
- **状态**：`implemented`（RED→GREEN 完成；全量测试绿、typecheck 绿、demo 复跑通过）

## 背景

审计清单 C1 #1：mini 的工具名与参数名和上游工具目录**完全不兼容**——模型按上游习惯调
`read`/`file_path` 会直接吃 `UnknownToolError`（且 M3 spec 自己写的就是 read/write/edit，
实现当初又改名成了 `read_file` 系）。用户拍板修复（选项 B：A + C1 #1）。

## 决策

模型可见面全部对齐上游（v0.1.0-rc.5 工具目录），其余语义零改动：

| 维度 | 旧（mini） | 新（= 上游） |
|---|---|---|
| 工具名 | `read_file` / `write_file` / `edit_file` | `read` / `write` / `edit` |
| 路径参数 | `path` | `file_path` |
| edit 参数 | `oldText` / `newText` | `old_string` / `new_string` |
| bash 参数 | `cwd` | `workdir` |

- **不动**：`ToolContext.cwd`（seam 内部执行上下文，上游内部也是 cwd 语义）；工厂/插件
  导出名（`createReadFileTool`/`readFileTool`/…，JS 标识符不是模型可见面）；工具**输出**
  形状（`{path,bytes}`/`{path,replaced}`，输出格式对齐是另一项未排期 C1）。
- **MCP server 的 raw 工具名不动**：`mcp.e2e` 用的官方 server-filesystem 自带
  `read_file`/`write_file` 是其 wire 名字，与 mini 的 fs 工具无关。
- 同步更新：`packages/tools`（fs/bash + 测试）、`packages/agent`（e2e 测试 + tools-demo +
  my-tools 练习脚本）、session/client/llm/test-support 各测试 fixture、
  `docs/tutorials/M3-tools.md`（时序图/声明示例/练习/FAQ/附录）、`M4-web.md` 工具卡片示例、
  `packages/tools/README.md`。
- 旧决策交叉链接：`2026-08-16-m3-tools-决策.md` 决策 5/6 标注"2026-08-18 修订"指向本 note。

## 影响

- 模型调用兼容性：按上游工具目录训练/书写的调用（`read`+`file_path`、`edit`+
  `old_string`）直接命中，不再 UnknownToolError。
- 教学一致性：M3 教程的示意图、示例与真实声明名终于一致（此前 spec 写 read/write/edit、
  实现用 read_file 系，教程跟着实现走——是审计发现的自我不一致）。

## 遗留问题（未排期）

- C1 #2 read 无 offset/limit/大小上限、C1 #5 edit 缺 `replace_all` 与空串/同串校验——
  同属"上游工具目录对齐"但涉及行为面（校验/分页），本次只做命名对齐未动行为。
- 工具输出形状（write 返回 `{path,bytes}` vs 上游 `operation` 等）未对齐。
